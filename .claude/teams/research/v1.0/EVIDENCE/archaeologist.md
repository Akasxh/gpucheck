## §3. The fuzzing strategy that found those bugs

Per README L213 "Most of the bugs we found in Triton tutorials were caught by
non-power-of-2 shapes -- dimensions like 17 and 127 that hit tile boundary edge
cases. This is exactly what `fuzz_shapes()` generates." Cross-checked against
`src/gpucheck/fuzzing/shapes.py:9-16`:
- `TILE_SIZES = (32, 64, 128)`
- `PRIMES = (7, 13, 31, 127, 257)`
- `POWER_OF_2_BOUNDARIES = (127, 128, 129, 255, 256, 257, 511, 512, 513)`
- `LARGE_DIMS = (2048, 4096, 8192)`

triton#9838 reproduced at `n_cols=17` (a non-power-of-2 + tile-mismatch) — this
is generated by `_non_tile_aligned_shapes` (32-1=31, 32+1=33, 32+3=35, ... and via
the prime list). triton#9839 reproduced at `K=8192` (a LARGE_DIM exact value).
**Both bugs lie in the active priority cells of the fuzzer**; the same priority
order applies to MPS without modification. This is the load-bearing observation
for Sub-Q 8.

## §4. Tolerance recalibration shows discipline

`6562f31 [Fix] : recalibrated tolerance tables from GPU measurements, fixed error
reporting cosmetics` is dated recent. The commit sequence
`9352672 → f7f84eb → 6562f31` shows the team has a habit of recalibrating
tolerances when the table drifts from observed reality. **For MPS, the same
discipline must apply**: ship table, run fuzz suite on M-series silicon, rebase
the MPS overlay against measurements. The skeleton for that workflow is already
in `apply_config_tolerances` and `tolerances_from_config` at `tolerances.py:91-125`.
