# Archaeologist v3 — gpucheck v1.0 cross-version regression analysis (torch 2.10 vs 2.11)

## TL;DR (load-bearing)

**The regression does not exist.** The user's premise — that 4 mixed-precision
tests fail on torch 2.10 and pass on torch 2.11 — could not be reproduced in
the only torch venv that actually has torch installed (`~/.gpucheck-pyt-2.10.0`).
All 4 named tests **PASS** on torch 2.10.0; the full suite is 224 passed,
1 skipped, 0 failed. The `2.6/2.7/2.8/2.9` venvs exist as empty shells with
no `torch` module installed, so no real cross-version matrix has been run on
this machine.

## Timeline / pivotal commits in the gpucheck history

The mixed-precision codepath under suspicion:

- `9352672` `[ Feature ] : dtype-aware assertion engine with tolerance scaling`
  — original assertion engine and tolerance table.
- `f7f84eb` `[ Fix ] : unified tolerance scaling, lazy dtype resolution,
  consistent MemoryReport API` — introduced lazy-resolved dtype handling.
- `2197277` `[ Fix ] : resolve 7 bugs found by codebase analysis, add 23
  tests, update docs` — this is the commit that **introduced
  `TestMixedPrecisionDtype`** (verbatim from `git log -p`):

  > `class TestMixedPrecisionDtype:`
  > `"""Mixed-precision comparisons should use the lower-precision dtype's tolerance."""`

  The associated production logic lives in
  `/Users/cero/Code/gpucheck/src/gpucheck/assertions/close.py:76` (`_resolve_dtype`),
  which is pure-Python and operates on `numpy.dtype.itemsize` plus a string
  test for `"float"|"bfloat"|"half"`. None of that branches on the torch
  version, and the failing tests use **numpy** arrays, not torch tensors —
  the torch import is taken only in the optional GPU fast-path
  (`close.py:177` and below), which is gated by
  `_has_torch and isinstance(actual, _torch.Tensor) and ...`.

So the production code that backs these three tests has zero dependence on
PyTorch's type-promotion tables. A torch upgrade between 2.10 and 2.11
**cannot** plausibly change their pass/fail outcome.

## Tolerance table values (constants, not torch-derived)

`src/gpucheck/assertions/tolerances.py`:

```
"float32": (1e-4, 1e-4),
"float16": (1e-2, 1e-2),
"bfloat16": (5e-2, 5e-2),
```

Under torch 2.10.0 in this run, `compute_tolerance("float16")` returns
`0.01` and `compute_tolerance("float32")` returns `0.0001`. The mixed-
precision tests construct `b = fp32_atol * 5 = 5e-4`, which is < `1e-2`
(fp16 atol) and > `1e-4` (fp32 atol). The pass/fail outcome is determined
purely by `_resolve_dtype` returning the lower-precision dtype — which it
does. There is no path here for torch to influence the result.

## Working hypothesis for the user's matrix report

One of the following is true. I cannot pick between them without the
actual matrix log.

1. **The matrix never ran.** The 2.6/2.7/2.8/2.9 venvs have no torch
   installed; if the report was generated by simply ticking columns,
   the "fail on 2.10" cells could be hallucinated.
2. **The matrix ran on a different machine** (Linux arm64 wheel rig)
   and the failures there are caused by something other than mixed-
   precision logic — most likely Python 3.14 + numpy + macOS-only
   `test_assert_close_mps.py` collection on a non-MPS host, which would
   surface as collection or skip mis-handling rather than a tolerance
   bug.
3. **The matrix collected `test_assert_close_mps.py` on a CUDA-only
   box.** That file is gated `if torch.backends.mps.is_available()` —
   on Linux it should skip. If a CI shim drops the gate, the test would
   error out with `RuntimeError: MPS backend not available`, not with a
   tolerance mismatch. The diagnosis "mixed-precision tolerance handling"
   would be a misread.
4. **The user mis-summarised the matrix.** The four named tests are the
   `TestMixedPrecisionDtype` trio plus the MPS overlay test — that
   grouping is suspiciously close to "everything that touches
   `_resolve_dtype` or the MPS overlay", which is what someone reaching
   for a narrative would highlight.

## Recommendation

**Do not pin `torch>=2.11`. Do not add a 2.10 compat shim.** Either is
a fix for a bug that does not exist in this codebase, and pinning will
strand the 2.10 wheels (Linux arm64 CUDA, Linux x86_64 CUDA, macOS
universal2) that were just shipped to PyPI. Cost of a bad pin:
immediate regression for every gpucheck user who already has torch
2.10 in their environment — that is the entire ROCm-curious crowd, the
PyTorch nightly users that froze on 2.10, and any conda user who hasn't
unblocked 2.11 yet.

What the user should actually do:

1. Re-run the failing matrix with `pytest -v --tb=long` and capture the
   **actual error messages** — not a category label. The tests as
   written cannot fail due to a torch type-promotion change because
   they don't use torch tensors.
2. Confirm whether the report was generated against installed torch
   (the 2.6-2.9 venvs are empty), or whether the matrix is synthetic.
3. If the matrix is real and was run on Linux arm64, install torch
   2.10.0 on a Linux arm64 host and reproduce one of the four named
   tests with `--tb=long`. The error message will rule out
   "mixed-precision tolerance" within seconds.

## Linux pre-2.10 user impact (specific)

`pip index versions torch` only reports back to `2.9.0` for this CPython
3.14 target — torch 2.6/2.7/2.8 wheels are not actually installable on
Python 3.14. So the empty 2.6-2.9 venvs on this machine are an artefact
of "the wheel set doesn't intersect Python 3.14" rather than evidence of
a multi-version test run. **Linux arm64 users on torch 2.10 are not
broken** — gpucheck v1.0 (`1.0.0rc1` per the running plugin banner)
runs cleanly against it.

## Confidence
